# GitHub 自动检查

SORS 0.1 · 2026-10-20

项目清单把文档、案例、环境和结果连起来，自动检查帮助维护这些连接。移动文件、增加案例或更新依赖时，贡献者可以及时看到需要补上的材料，维护者也更容易把注意力放在方法和结果上。

## 本地结构检查

在社区仓库安装开发依赖后，指向需要检查的项目：

```bash
python -m pip install -r requirements-dev.txt
python standards/SORS/tools/check_project.py --root /path/to/project --report /tmp/sors-report.json
```

结构检查覆盖必需字段和类型、非空主文档与许可证、列表 ID、项目与案例身份、环境引用、步骤依赖、输入与输出引用、材料路径、主文档的本地链接。越出项目根目录的路径与符号链接会报错。`observed` 结果必须指向实际记录，`not_bundled` 材料提供取得说明。

主文档可以共用一份文件；计划案例可以沿用已整理的材料。科学计算报告中的失败、未定结果和历史差异都可以正常保留，结构检查根据材料与声明的一致性判断。

报告区分 `structure`、`execution` 和 `scientific_review`。仅运行结构检查时，执行状态为 `not_run`，科学审阅为 `pending`。判断标准和专业模型的适当性由对应领域的审阅继续处理。

## 按需运行小型案例

在项目所声明的环境中，可显式选择已有命令：

```bash
python standards/SORS/tools/check_project.py --root /path/to/project --case example --step compute --run --report /tmp/run-report.json
```

有依赖时重复 `--step`，把需要运行的前置步骤一起列出。检查器按依赖顺序执行所选步骤，命令失败或超时后停止后续执行。仅有操作说明的步骤需按文档完成。所选步骤的 `output_refs` 需要对应 `outputs.path`，检查文件是否由本次运行生成或更新；具体数值与文件内容由项目检查脚本负责。

命令可以执行项目代码；请在适合该代码的环境中运行。路径检查和参数数组帮助规范入口，操作系统权限与进程隔离由本地环境或 CI 运行器提供。大型扫描、外部商业求解器和需专门硬件的计算可以另行安排。

## GitHub 中的共同入口

[公共工作流](../../.github/workflows/sors-project-review.yml)执行结构检查并保存报告。调用方把工作流与 `checker-ref` 都固定到已经审阅的完整社区提交号，在升级检查器时一起更新。项目内容与公共检查器分别取得，结构作业不执行项目安装步骤和科研代码。

公共作业使用 GitHub 托管的 Linux 运行器、只读仓库权限、关闭持久凭据的 checkout 和固定提交号的官方 Actions。项目的轻量测试放在独立作业中；不使用 `pull_request_target` 执行贡献者代码，不为这些作业提供私密凭据。工作流定义和检查器版本变化由维护者审阅。

PR 的[维护提示](tools/summarize_changes.py)列出变动的索引、依赖、检查程序和参照路径。对于项目或案例索引，会进一步指出环境、方法、判据、结果等哪些部分变化。提示帮助安排复核，影响范围仍需结合实际依赖阅读。

## 当前范围与后续完善

当前实现检查本地连接和明确选择的命令；外链在线状态、文档章节锚点、结果数组的专业含义、科学容差和所有传递依赖暂不由通用检查器判断。领域项目可以追加自己的文件格式、单位、形状和数值检查，并在案例中登记入口。

后续改进可围绕实际维护问题展开：失效引用的修复建议、结果文件摘要、案例影响范围及不同平台的小型运行。增加检查时，配上能够辨认通过与失败的例子，使检查器本身也方便审阅和维护。
