# SORS 项目参与与维护规范

v0.1 · 2026-10-20

将项目带到社区时，一份清楚的介绍、能跟着运行的案例和方便核查的结果，能够帮助别人更快理解你的工作。这里约定项目需要准备的基本材料，以及后续贡献怎样保持这些材料可用。

通用研究方法论由社区共同维护，项目可以引用。开发故事和个人经历由作者自愿分享，日常参与不要求提交详细协作过程。

项目和案例使用 SORS 0.1 索引，配套 Schema 和检查器随本规范一起维护。

## 展示完整项目，选择轻量入口

基本要求帮助新参与者找到起点，项目介绍同时呈现已经形成的完整能力和研究成果。已有多篇文献计算、多个工具模块或独立验证基准的项目，应提供相应目录，说明各自完成的工作与结果位置。一个入门案例用于帮助读者开始使用，其他成果同样进入项目索引。

项目的展示范围、第一次运行的计算量和CI每次执行的检查范围可以分别安排。完整能力目录可以连接大型研究；快速开始选择短小例子；自动检查按改动运行必要部分。这样既能方便初次使用，也能让读者看见项目的实际积累。

## 1. 统一信息，允许沿用目录

新项目推荐以下骨架。文件名中的可合并部分可以由索引指向现有文档，不必制造空目录或复制相同内容。

```text
project/
├── README.md                  # 项目介绍、状态、入口
├── research.yaml              # 项目提交清单
├── LICENSE                    # 自有代码或主要资产的许可
├── RESEARCH.md                # 问题、模型、方法、主要能力和范围
├── CONTRIBUTING.md            # 参与、维护与反馈入口，可链接社区通用规则
├── src/                       # 实际代码；也可为项目已有目录
├── docs/
│   ├── RUN.md                 # 安装、输入、命令；可合并进README
│   └── SOURCES.md             # 第三方来源、许可、项目引用方式
├── cases/
│   └── example/
│       ├── case.yaml          # 案例索引与状态
│       ├── CASE.md            # 研究问题、条件、方法、判断依据、局限
│       └── results/           # 已有结果；也可指向版本化外部资产
└── tests/                     # 有自动检查时提供；手工检查也可明确声明
```

源码可以位于 `src/`、包目录或原有模块目录；案例可以保留 `studies/`、`research_cases/`、现有报告目录。索引负责定位。对探索或非代码研究，不要求不存在的源码、测试和结果目录。

根目录保存唯一的项目清单：`research.yaml`、`research.yml` 或 `research.json`。三种文件均使用 SORS 0.1 结构。原有 `schema_version: 1` 起步清单可继续用原检查器维护，迁移时转换字段并保留已有结果与判断。

## 2. 为使用者准备的基本材料

| 部分 | 最小内容 | 允许的承载方式 |
| --- | --- | --- |
| 项目说明 | 项目名称、要解决的问题、当前状态、实际维护者、主要入口 | README |
| 研究说明 | 研究问题、模型与假设、方法及依据、主要能力、适用范围与已知局限 | RESEARCH.md或已有文档；小项目可合并 |
| 代码与研究材料 | 代码、数据、模型或其他已有成果的位置；尚无可运行成果时说明进展 | 现有目录或带版本的外部资源 |
| 使用条件 | 支持平台、依赖、安装和使用方式、输入取得方式、所需资源 | RUN文档与环境文件；探索阶段说明待具备条件 |
| 研究案例 | 至少一个具体案例的索引，状态为计划、可运行或已有结果 | case.yaml及案例文档；已有结构可映射 |
| 验证和结果 | 怎样检查、参照什么、检查覆盖范围；已有结果的实际位置与状态 | 案例文档、检查脚本、结果报告；未运行应写明 |
| 来源与许可 | 自有资产许可、第三方来源与使用范围、引用本项目的方式 | LICENSE及来源文档；不要求所有项目使用同一种许可证 |
| 维护和参与 | 谁维护、如何反馈、如何提交贡献 | CONTRIBUTING或README中的明确入口 |

一项内容可以引用另一份已有文件。检查器判断是否有有效引用，不要求每一项都单独创建 Markdown。

## 3. 案例必须说明的内容

案例描述一个科学问题或实际用途，并说明：输入和来源；模型、假设与关键参数；计算或研究方法；运行或操作步骤；判断依据和验证方式；结果状态与结果位置；局限和未解问题。

这些内容共同连接案例的研究问题与实际材料。方法说明介绍当前采用的路线和科学依据，不要求重建讨论历史或逐轮解释谁提出了什么。相同模型、环境和许可可以引用项目层声明。

### 按实际状态补充材料

| 案例状态 | 需要具备 | 不应要求 |
| --- | --- | --- |
| 计划案例 | 明确问题、已有输入、拟用方法、反馈计划和当前缺项 | 尚未发生的运行结果、伪造的通过状态 |
| 可运行案例 | 输入取得方式、环境与命令、预期输出说明、实际最小运行记录 | 对所有平台承诺兼容、重跑整篇论文 |
| 已有结果案例 | 对应配置、代码版本或源文件摘要、结果位置、检查报告与解释范围 | 全部科学问题解决、论文所有面板吻合 |

案例阶段、当前可运行性、检查结果和科学审阅分别记录。历史案例可以已有结果，但当前环境尚未恢复；清单应同时表达这两个事实。“已有结果”可以包含失败或未定结果，不能被理解成科学通过。项目如宣称已有独立验证，应指向实际检查及覆盖范围。

## 4. 让导航和维护工具找到材料

项目和案例索引保存各类说明的位置。维护者更新路径或新增案例时，导航与检查工具可以一起跟进；科学解释继续保存在便于阅读的文档中。

整理方式见[项目组织指南](FORMAT.md)，字段、类型和引用规则集中在[技术附录](TECHNICAL-FORMAT.md)。已有资料可以先引用正文，再按实际维护需要补充结构化内容。

**项目清单**提供：契约版本；项目 ID、名称与维护者；当前范围；README和研究说明的位置；许可、来源和贡献入口；代码或资产位置；案例列表；适用领域扩展。可运行项目再给环境文件、支持平台、安装/最小运行/检查命令及超时。命令可以引用现有执行契约，保持唯一来源。

**案例清单**提供：案例 ID、名称、实际阶段；案例说明；模型和输入配置的位置；使用的项目能力；运行入口或项目入口引用；验证方法与状态；结果位置及可用的生成版本；限制说明。计划、未运行、手工核查、失败和通过应明确区分。

环境、模型输入、方法入口、参考依据、验证标准、输出结果和版本来源应能分别定位，并由同一个案例连接。项目有多个环境时，案例引用实际环境；参考资料说明用于哪项比较；主要结果提供字段/数组含义及生成记录。具体内容见[研究材料复用说明](REUSABLE-MATERIALS.md)。它们可以引用现有文档、配置和脚本，不要求新建七份文件。

最小规范不要求对每句话建立 claim ID，不要求决策事件数据库，也不要求新的运行平台。案例、命令、配置和结果的简单引用即可承载首版交付。

需要自动比较的数值提供单位、指标和容差；研究计划说明准备怎样检查即可。大文件可以指向稳定的版本化下载地址，给出大小、摘要和取得说明，无需全部纳入 Git。

## 5. 领域专有部分

领域扩展由项目声明名称与版本，包含触发条件和所需字段，引用既有配置。未触发的要求不适用。

- 计算光子学可以声明几何、材料、单位和频率约定，涉及开放辐射时再声明边界与损耗处理；模式身份和空间/模态/时间截断按目标计算说明。
- 生态动力学可以声明状态方程、变量和扰动度量；时滞案例再声明历史函数，随机案例再声明种子及样本单位，事件案例再声明阈值和停止规则。

脚本检查字段与引用是否完整，项目指定的数值检查验证可执行关系。专业条件是否适当仍由审阅者判断。

## 6. 首轮接入与后续修改

首次接入检查整套提交清单和选定最小案例。后续 PR 检查变化涉及的格式、链接、依赖、代码和案例；文档修改无需重跑所有实验。新增能力应补相应使用说明或案例，新增结果应关联输入和版本。

删除接口、移动结果、改变模型/参照/阈值或更新关键依赖时，检查器提示受影响项目；说明可写在普通 PR 描述中，无需专门的协作回顾文件。影响结论或科学判据的改动由维护者复核。

详细自动检查建议见[GitHub 检查说明](GITHUB-CHECKS.md)。
