# 自动检查与人工审核

## 四种结果分别呈现

1. **交付结构**：必要文件、有效链接、表单、元数据是否完整。
2. **可运行性**：声明平台上的安装与最小案例是否执行成功。
3. **自动验证**：是否执行了声明的验证命令，其退出码是否成功。验证覆盖范围必须另读证据。
4. **人工科学审核**：主张、假设、独立参照、局限是否得到适合人员检查。

CI 不能认证科学正确性。`research-report.json` 只记录实际执行的阶段；没有 verify 的探索项目必须明确显示 `not_run`，人工科学审核始终从 `pending` 开始。

## 公共仓库

`Community review / structure-and-policy` 检查文档、本地链接、表单和生成配置；运行验证器自身测试。`Community review / review-sensitive-changes` 列出 reference、tolerance、criteria、research.json、验证代码及工作流等敏感修改。后者成功只表示检测器执行成功；列表中的修改仍需人工检查。

公共仓库没有科学模型，因此不显示“科学验证通过”。科研仓库采用参考包中的 `Research review` 工作流。

## 科研仓库

`structure-and-policy` 检查 research.json，`run-declared-checks` 在临时 Linux runner 中执行安装、最小案例与验证。仅接受清楚声明的平台；长时工作需要将小型案例与完整复现分开。

如果验证标准、参考数据、依赖或审核器本身改变，维护者必须阅读差异。自动提示是辅助，不能防止提交者同时改实现与检查。公开仓库发布后要求 PR 与必要检查。首期只有一位已确认维护者，平台不强制第二人批准；科学审核依靠公开记录，未独立审核的状态继续保留。维护者增加后再强化批准要求。

## 工作流边界

PR 的代码和安装命令本质上可执行任意代码。只在无生产凭据、只读 token 的临时 GitHub runner 执行；不用 self-hosted runner，不用 pull_request_target，不将申请人的 API 密钥提供给工作流。首次外部贡献可能需要 GitHub 的工作流运行批准。

第三方 Actions 固定到经核验的提交。GitHub Free 资源用量仍受其限制；不承诺无限 CI 算力。

## 合并前的人工记录

- 工程检查：检查了什么，结果如何。
- 科学判断：具体主张、证据、未覆盖范围。
- 参考或容差变化：理由及是否改变了原结论。
- 审核者与作者关系：是否独立；无人独立审核则如实说明。

## AI Review

首版提供 [人工发起的 AI 审阅提示](AI-REVIEW.md)，不启用自动外发代码的机器人。没有执行模型调用时，不称为 AI Review 已上线。未来接入需要确定服务、预算、仓库内容可发送范围和凭据管理；输出仍作为建议，不能自动批准科学结论或合并。
