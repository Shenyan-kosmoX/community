# 提交以后怎样审核

审核帮助作者与使用者确认：材料能找到，使用入口能跟上，结果也有可以讨论的依据。项目采用 [SORS 0.1](../standards/SORS/README.md)，共同检查和各项目自己的验证相互配合。

## 首次接入项目

先在[项目提案区](PROJECT-INTAKE.md)介绍用途与进展，再整理准备公开的版本。维护成员一起查看项目的完整能力、案例目录、运行条件、来源与许可，并选择一个合适的使用入口核对。

整理后的索引由公共检查器核查。计算和操作是否顺利，结合项目的小型测试与实际运行记录判断；专业模型和结果解释则进入相应的科学审阅。

## 各类检查分别看什么

| 环节 | 主要内容 | 怎样阅读结果 |
| --- | --- | --- |
| SORS 结构检查 | 字段和类型、ID、项目与案例关系、环境与步骤引用、文件位置、主文档本地链接 | 表示提交材料按约定连接起来；默认执行这一层 |
| 项目运行检查 | 安装、选定案例、测试、退出状态和声明产物 | 结合实际平台、依赖版本和运行范围阅读 |
| 科学与方法审阅 | 模型、参照、验证设计、结果解释、适用范围和未解差异 | 审阅者记录依据与判断；按当前研究问题确定需要的检查 |

公共报告分别使用 `structure`、`execution` 和 `scientific_review`。只执行结构检查时，运行状态显示 `not_run`，科学审阅显示 `pending`。项目自己的 CI 可以补充软件与数值检查；人工审阅再把这些检查与具体结论联系起来。

例如，EcoDynamics 同时检查多个 Python 与操作系统环境；Floquet–Maxwell 的软件 CI 包含接口控制、实际 Legume 小网格计算和绘图。每项检查的范围都在项目工作流和运行记录中说明。完整科研成果仍通过案例目录展示。

## 提交改动

创建 PR 后，自动检查结果会显示在页面下方。检查失败时，打开对应记录定位错误，修正后继续提交到同一分支即可。

较小贡献和日常修改由内部成员审核。普通 PR 描述写清改动及验证方式就够了。模型、参考数据、容差或检查程序发生变化时，补充修改理由和受影响的结果；维护提示会帮助审核者发现这些变化。

文档修正侧重链接和表达，接口修改配合相关测试，新的科学结果附对应输入与证据。检查范围根据实际影响安排。

## 结果有分歧

把各自的观察、依据和仍有疑问的部分留在 PR。需要更多人一起讨论时，在 [Discussions](https://github.com/Shenyan-kosmoX/community/discussions) 发帖并回链 PR。维护成员说明本次接受哪些修改、采用什么解释，以及哪些问题继续讨论。

科学审阅记录检查人、版本、范围与结论。数值、实现、模型和来源假设造成的差异可以分别保留，后续贡献者能够沿着这些线索继续核查。

## 具体操作

检查命令、环境与工作流设置见[维护说明](OPERATIONS.md)；SORS 的实现范围见[GitHub 自动检查](../standards/SORS/GITHUB-CHECKS.md)。借助 AI 阅读改动时，可以参考 [AI 审阅提示](AI-REVIEW.md)。
