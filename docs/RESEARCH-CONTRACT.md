# 怎样整理一份别人能用的项目

第一次使用的人通常想知道：这个项目能帮我做什么，怎样开始，以及运行以后该看什么。整理交付时，围绕这些问题准备材料。

## 每个项目都可以先准备这几件事

- 一段介绍：为什么开发、解决什么问题、作者与维护联系人。
- 一个使用案例：需要什么输入，怎样操作，输出是什么。
- 一份检查说明：你怎样确认它工作正常，哪些情形还需要改进。
- 明确版本、依赖和许可，方便别人取得同一份材料。
- 后续工作和贡献入口，让有兴趣的人知道能从哪里加入。

[开发记录](DEVELOPMENT-NOTES.md) 可以讲述方法选择和学习经历，随项目逐步补充。

## 根据项目选择检查方法

科学计算项目说明模型、参数、基线与数值验证。Skill 和内容工具可以使用一组具体输入，检查内容完整性、输出格式、复制或导出结果，并附适合人工比较的样例。作者需要说明检查的是哪种使用情境。

下面的运行协议和自动审核参考包面向 Python 科研计算项目。其他工具可保留已有构建和测试方式，在项目中提供相应命令与说明。

## 文件与版本

代码、文档、必要小型数据进入 Git。大文件通过版本化 Release 或有明确许可的存储提供，记录稳定地址、大小与 SHA-256。把运行所需的输入和缓存取得方式写清楚，方便别人从自己的电脑开始。

`research.json` 描述一个版本的运行入口和证据位置。环境声明至少包含：Python 版本、支持平台、依赖文件、实际项目联系人、许可说明、最小案例、验证方式及限制。

## 任务类别

| 类别 | 验收关注 |
| --- | --- |
| reproduction | 对应论文或独立基线、固定条件、可比观测量、已知差异 |
| development | 新增能力、接口、适用范围、回归与独立控制 |
| exploration | 问题、方法、过程与证据质量；允许阴性或未定结果 |

## 判断依据

**验收依据**说明怎样算完成；**独立参照**给出比较所用的结果或方法；**验证方法**记录具体怎样检查。把这三件事连起来，读者就能理解一次测试支持什么结论。

物理结果的证据要求应对应主张、观测量和相关尺度。数值收敛、实现错误、模型表示限制和来源不确定性分开记录。不为了通过审核追溯放宽容差。

## 命令

命令以参数数组记录，审核器不使用 shell 拼接。`install` 在独立环境安装项目依赖；`smoke` 运行最小案例；`verify` 运行与证据有关的检查。没有自动科学验证的探索项目可以将 `verify` 留空，但必须说明人工审核方法，此时报告为“未执行自动科学验证”，不能显示验证通过。

记录每个命令的超时预算，以及实际支持的平台。重型计算可人工运行并附机器、版本、时长和结果，在报告中与 CI 的小型检查分别呈现。

## 结果与授权

保留模型假设、配置、输出、差异和失败。参考材料应有来源与许可；私人轨迹不属于默认交付。贡献认可见 [引用与认可](RECOGNITION.md)。
